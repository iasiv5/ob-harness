# 经验沉淀的分层判定与通道选择：一条经验该写到哪一层、走哪条通道

## 元数据

- **类型**: BestPractice
- **适用场景**: agent（本地的或别人环境的）在会话中踩了坑/学到经验后，决定它该沉淀到哪一层记忆时
- **创建日期**: 2026-07-28
- **来源**: `ob init gb200nvl-obmc` 冷启动误用 dry-run 事件。坑本身 workflow_01 line 156 已记，但 meta 问题"这条经验为什么只进了会话记忆、没进仓库分发"暴露了分层判定规则的缺位。

---

## TL;DR · 30 秒决策（只读这段也能用）

一条经验该写到哪层？按顺序问，命中即停：

1. **源于 ob-harness 自身的设计/文档/流程吗？** 否 → 仅记会话记忆（或丢弃），不污染仓库。
2. **别的用户环境会同样踩吗？** 会 → 必须进仓库分发层（`rules/knowhow/` 或 `contexts/memory/`）；不会 → 仅记会话记忆。
3. **进仓库的哪个子层？** 价值观/决策原则 → `axioms/`（先查覆盖）；具体 workflow 的操作步骤/陷阱 → 该 workflow 的"已知陷阱"段；跨 workflow 的沉淀方法论 → 新建 `bestpractice_*.md`；一次性观测 → `contexts/memory/OBSERVATIONS.md`（🔴 级满足问2时应晋升为 axioms/know-how；手动通道晋升后原观测保留、自动化通道 reflector 会删——见「沉淀通道」）。

**落盘即收口**（强制三件套）：覆盖检查 → 写入 → 更新入口（KNOWHOW_INDEX / AXIOMS_INDEX）→ terminal 直读磁盘核实。

> 详尽的分层架构表、反模式、验收标准见下文各段。本块用于快速决策，**不省略落盘即收口和覆盖检查两步**。

## 沉淀通道：自动化 vs 手动（两条并存，都合法）

动手判定"写到哪层"之前，先认一条更顶层的事实：经验沉淀进 ob-harness 仓库有**两条通道**，并存且都合法，按经验形态选择。

| 通道 | 入口 | 适用场景 | 晋升 / 原观测去留 |
|---|---|---|---|
| **自动化** | `/ai-heartbeat`（ai_heartbeat 工具，执行合同见 `periodic_jobs/ai_heartbeat/docs/` 三份文档） | 日常渐进观测的蒸馏 | observer 把当天观测追加到 `OBSERVATIONS.md` → reflector 把共性经验晋升到 `rules/`，并按 `KNOWLEDGE_BASE` §4.2 第 3 项做 GC：**删除已被固化进 rules 的内容** |
| **手动（本文件主讲）** | agent 在会话中按本文件"三问路由"直接判断、直接写 | 解决具体问题时即时沉淀的高浓度经验 | 不强制经 `OBSERVATIONS.md`；若原观测已在 OBSERVATIONS，手动晋升后**保留**，不走 reflector 的 GC |

要点：

- 两条通道**并存且都合法**，不是二选一。本文件聚焦**手动通道**的分层判定。
- 两条通道产出 `rules/knowhow` 的纪律一致：落 know-how 先读 `bestpractice_01`、落完更新 `KNOWHOW_INDEX`（自动化通道见 `KNOWLEDGE_BASE` §4.2 第 2 项）。
- 由此解释一处口径差异：手动通道晋升后 OBSERVATIONS 原观测**保留**（见下文问 3 表格）；自动化通道 reflector 则**删除**已固化内容（§4.2 第 3 项）。两者不矛盾——属不同通道。

> 实例：本文件、`bestpractice_11`、`workflow_01` 的 2026-07-28 新增都走**手动通道**（元数据"来源"是会话即时事件，`OBSERVATIONS.md` 无 2026-07-28 条目）；而 `OBSERVATIONS.md` 中 ob 优先（→ `bestpractice_06`）、深模块抽取（→ `bestpractice_10`）那几条 🔴 晋升后仍保留，正是手动通道未走 reflector GC 的痕迹。

## 核心盲点

**踩坑后的第一反应是"记下来"——然后往会话记忆（agent/harness 私有记忆，如 `/memories/`，位于本仓库之外）里一塞就算完事。**

这个盲点的危害不是"没记住"，而是**记错了层**：

- 会话记忆（`/memories/`）**只帮当前这一个 agent**，新会话/别的 agent 看不到，更不会随 ob-harness 仓库分发给别人。
- 仓库层（`rules/`、`know-how`）才**随仓库分发**，对"使用 ob-harness 产品的所有 agent"都有效。

把一条**源于 ob-harness 自身、别的环境会同样复发**的经验只塞进会话记忆，等于把"产品的缺陷"当成"我个人的健忘"来处理——产品缺陷还在那里，下一个用户照样会踩。ob-harness 作为产品的价值闭环，要求这类经验必须回流进仓库，而不是烂在某个 agent 的本地记忆里。

## ob-harness 的分层记忆架构（权威口径）

判定前先认清每层的地位，**"自动加载"和"随仓库分发"是两个独立维度**：

| 层 | 典型位置 | 随仓库分发? | 自动加载? | 谁受益 |
|----|----------|:-----------:|:---------:|--------|
| **公理 / Axioms 索引** | `rules/axioms/*` + `06_AXIOMS_INDEX` | ✅ | ❌（按需检索，`06_AXIOMS_INDEX` 是 axioms 检索入口，非每会话自动加载） | 所有使用者 |
| **核心规则 Rules** | `rules/01_SOUL`~`05_KNOWHOW_INDEX` | ✅ | ✅（每会话启动读） | 所有使用者 |
| **Know-how** | `rules/knowhow/*` | ✅ | ❌（`05_KNOWHOW_INDEX` 自动加载给一行摘要，全文按需） | 所有使用者 |
| **L1/L2 动态记忆** | `contexts/memory/OBSERVATIONS.md` | ✅（文件分发，内容本地累积） | ❌（按需检索） | 所有使用者（但内容是本环境的观测，未必通用） |
| **agent 会话记忆** | agent/harness 私有记忆（如 `user memory`，本仓库之外，不随 ob-harness 分发） | ❌ | 部分（自动加载部分内容） | **仅当前这一个 agent / 这一台机器** |

两条由此直接派生的约束：

1. **只随仓库分发的才算"产品级"沉淀**。"使用 ob-harness 的人"能受益的，只有 `rules/`、`know-how`、`contexts/` 这三棵树。会话记忆对别的用户完全不可见。
2. **自动加载 ≠ 分发**。会话记忆/核心 Rules 自动加载是为了"省检索成本"，但 KNOWHOW_INDEX 自动加载的是**摘要**、axioms 全文不自动加载——所以"自动加载层有这条提示"和"仓库文档里有这条警示"是两件事，判断落点时不要混淆。

## 分层判定：三问路由

遇到一条刚学到的经验，按顺序问下面三个问题，命中即停、落到对应层：

### 问 1：这条经验是不是源于 ob-harness 自身的设计/文档/流程？

- **是**（如：workflow_01 的某个陷阱、`ob` 某个子命令的行为、某条 know-how 的缺失） → 进 **问 2**
- **否**（纯环境事故、与 ob-harness 无关的通用编程坑） → **仅记会话记忆**，或直接丢弃。这类经验不会随仓库带给别人任何价值，塞进仓库是噪音（违反 A05 §4.1"保存一切"陷阱）。

### 问 2：别的 agent / 别的用户的环境会不会在同等条件下同样踩？

- **会**（系统性缺陷、文档覆盖盲区、所有使用者都会遇到的流程陷阱） → **必须沉淀进仓库**（`rules/knowhow/` 或 `contexts/memory/`）。这是产品价值的回流点。
- **不会**（纯属本会话的偶然，或仅特定环境的特例） → **仅记会话记忆**。不要用一次性偶然污染仓库。

### 问 3：沉淀进仓库时，放在哪个子层？（仅当问 2 命中"会"）

按"通用性 × 是否可执行判定"选：

| 经验特征 | 落点 | 判定理由 |
|----------|------|----------|
| 触及受众所认同的**价值观/决策原则**（为什么这样做） | `rules/axioms/`（候选公理；先检查是否已被现有公理覆盖） | 公理是思考层，启发而非执行 |
| 某个具体 workflow/bestpractice 的**操作步骤或已知陷阱** | 对应 know-how 文件的"已知陷阱/故障排除"段 | 操作层经验就该跟操作层文档在一起，让读者在用那条 workflow 时就能看到 |
| 跨 workflow 的**经验沉淀方法论本身**（怎么判定、怎么写） | 新建一条 `rules/knowhow/bestpractice_*`（本文件就是先例） | meta 经验不该挤进任何单条 workflow |
| 一次性观测、项目快照、近期决策背景 | `contexts/memory/OBSERVATIONS.md` 按优先级分级（🔴/🟡/🟢） | 动态记忆，按需检索，定期 GC。**注意：OBSERVATIONS 是中转站不是终点**——🔴 级观测（跨项目通用、影响架构）满足问2"会复发"时，应在 axioms/know-how 再落一份（晋升）；原观测去留按通道分：**手动通道**晋升后 OBSERVATIONS 原观测**保留**（额外 Duplicate，不是搬走）；**自动化通道**的 reflector 会按 `KNOWLEDGE_BASE` §4.2 第 3 项**删除**已固化内容。见上「沉淀通道」 |

**覆盖检查（强制前置）**：落进任何仓库层之前，先查那里是否已经写过同类内容。
- 进 know-how 段前：grep 同目录，别和现有"已知陷阱"重复。
- 进 axioms 前：读 `06_AXIOMS_INDEX.md` + 相关公理全文，确认不是已有公理的换皮（A05/A10 已覆盖"文档是记忆"这类哲学命题，就不要再造重复公理）。

## 逃避责任的反模式

以下是"看起来沉淀了、实际没用"的典型逃避，自检时逐一排除：

1. **只写会话记忆，不写仓库**：当场见效，但下一个用户/下一个会话照样踩。判定标准——如果这条经验源于 ob-harness 自身，只写会话记忆就是逃避产品责任。
2. **写得极度抽象**：「要更仔细地读文档」「注意陷阱」这类没有触发条件、没有落点、没有可执行判定的"总结"，是披着经验外衣的废话。A05 §4.1 已警告"信息密度下降导致理解能力下降"。
3. **塞进不相关的层**：把操作坑塞进 axioms（滥用思考层），或把一次性观测塞进 know-how（污染操作层）。层错配会让后续 agent 在错误的检索时机遇到它，降低信噪比。
4. **重复已有内容**：workflow_01 已写明"冷启动 dry-run 无效"，再在某处抄一遍只是噪音——沉淀前**必须查覆盖**，已有就只更新触发条件/边界，不复制正文。
5. **沉淀完不更新入口**：新 know-how 不进 `05_KNOWHOW_INDEX.md`，等于没写（别人按索引检索找不到）。见下"落盘即收口"。

## 落盘即收口（强制）

沉淀到仓库层不是"创建文件"这一步，至少包含三件：

1. **覆盖检查**（grep + 读候选落点）——确认不是重复。
2. **写入正确层**（按"问 3"路由）。
   - 若落点是 know-how（新建/重写 `bestpractice_*.md` / `workflow_*.md`）：**先读 `bestpractice_01-knowhow_writing.md` 再动手写**——本文件只解决"写到哪层"，"那一层怎么写"交给 bestpractice_01（与自动化通道 `KNOWLEDGE_BASE` §4.2 第 2 项的 reflector 规范一致）。
3. **更新自动加载的入口**：
   - 新建 know-how → 必须在 `rules/05_KNOWHOW_INDEX.md` 对应分类下加一行入口（否则按需加载的 agent 找不到，等于白写）。
   - 新增/修订核心规则选段 → 若希望它进"每会话自动加载"，确认它落在 `rules/01`~`05`（这 5 个文件每会话启动读）；`06_AXIOMS_INDEX` 是按需检索的 axioms 入口，放进 06 ≠ 每会话自动加载。
   - 升级公理 → 必须登记进 `rules/06_AXIOMS_INDEX.md` 的分类表 + 写相关公理的"相关公理"交叉引用。

**验证**：写入后用 terminal 直读磁盘核实——`.md` 编辑可能静默失败，别信工具的"成功"，用 grep / tail 核实（**无论走哪个通道**；完整 fallback 链 tail→heredoc→二次验证已在 `periodic_jobs/ai_heartbeat/docs/AI_HEARTBEAT_SOP.md`「写入工具注释」节定义，不必在此重述）；新 know-how 进了 INDEX 就 grep INDEX 确认入口存在。

## 与现有体系的关系

- **A05 文档即长期记忆**（why）↔ 本文件（how-to-judge）：A05 讲清了"为什么文档是记忆、保存一切的陷阱"，本文件给出"具体一条经验该落到仓库哪一层"的判定路由。公理在前，判定在后，**本文件不重复 A05/A10 的哲学论证**。
- **A10 默契优于原始智能 §4.2**：A10 已强调"把默契外化为可转移形式，切换 AI 也能连续"——本文件是这条公理在 ob-harness 具体仓库结构上的执行细则。
- **bestpractice_01-knowhow_writing（怎么写 know-how）**：本文件是它的前置——"**先把经验路由到正确的层**，再谈怎么把那一层的内容写好"。顺序错了（先想怎么写，没想写到哪），写出来的东西落点就错。
- **contexts/memory/OBSERVATIONS.md 的 🔴/🟡/🟢 分级**：那是 L1/L2 动态记忆**内部**的优先级排序；本文件解决的是"经验该不该进 OBSERVATIONS、还是该升级到 rules/know-how"。前者管"同一个文件里记多详细"，后者管"该不该进这个文件"。两个判定不重叠。

## 验收标准

一个无上下文 agent 据此即可自检沉淀是否做对：

1. 每条经验沉淀后，是否确认过它**源于 ob-harness 自身还是纯属环境/个人**？前者才进仓库。
2. 源于 ob-harness 的经验，是否**确认过别的用户环境会同样复发**？会复发才进仓库分发层，否则仅记会话记忆。
3. 选定仓库子层时，是否做了**覆盖检查**（grep / 读 INDEX / 读相关公理全文），确认不是已有内容的重复或换皮？
4. 落盘后是否**更新了对应入口**（新 know-how 进 KNOWHOW_INDEX、新公理进 AXIOMS_INDEX），并用 terminal 直读磁盘核实内容真的生效？
5. 是否避免了把操作坑塞进 axioms、把一次性观测塞进 know-how 这类**层错配**？

## 已知陷阱

| 陷阱 | 表现 | 应对 |
|------|------|------|
| 只写会话记忆就当完事 | 源于 ob-harness 的经验只进 `/memories/`，下个用户照样踩 | 问 1+问 2 命中"源于自身 + 会复发"→ 强制进仓库分发层 |
| 把"怎么写"想在"写到哪"前面 | 还没定层就开始纠结措辞 | 先走三问路由定层，再参考 bestpractice_01 写那一层 |
| 重复覆盖已有经验 | workflow_01 已记的坑，在别处抄一遍 | 落盘前强制 grep + 读候选落点 + 读相关公理 INDEX |
| 落了文件忘了入口 | 新 know-how 不进 KNOWHOW_INDEX，等于隐形 | "落盘即收口"第 3 步是硬约束，写完必更新入口并核实 |
