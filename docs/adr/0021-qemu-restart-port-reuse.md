# `ob start-qemu` restart 端口沿用（kill-and-restart 复用旧实例端口）

`ob start-qemu` 检测到 running 旧实例、用户交互确认 "kill and restart" 后，`qemu_prepare_launch` 的端口解析**忽略** `PIDFILE_*`、从默认值（SSH 2222 / Redfish 2443 / IPMI 2623）重新解析——而默认 IPMI 2623/udp 常被内核残留 UNCONN socket（owner=`?`）占用，触发 `resolve_qemu_ports_interactive` 弹 prompt 要用户重输。根因：端口解析链缺失"旧实例端口"这一 fallback 层。经 `/grill-with-docs` 六决策锁定：restart 定义为"同 machine 存在 running 旧实例且本次会 kill 它"，交互确认路径把旧实例端口注入 `QEMU_*_PORT`（CLI flag 层）做端口复用，`-z` guard 保 CLI flag 优先，放弃软特权（D5 翻转：注入端口主治痛点、软特权语义反转，见 Consequences）；`--force` ≠ restart、不注入。本 ADR 记这条 load-bearing 决策。术语见 CONTEXT.md `重启 (restart)` / `端口解析链`。

Status: accepted — deploy guard 不对称（old_first）经 [ADR-0022](0022-port-reuse-resolver-module.md) 统一为 cli_first；下文 deploy 注入代码块及 `qemu_commands.sh:367-370` 行号反映 pre-0022 历史（行号且已漂移至 375-378，0022 后该注入 ritual 移入 module，此处保留作决策日志）

Amends: `cmd_start_qemu`（`lib/qemu_commands.sh`）交互确认分支新增旧实例端口注入（`-z` guard 到 `QEMU_*_PORT`）；`lib/qemu.sh` 不改（D5 翻转为无特权）。新增 CONTEXT.md 术语：`重启 (restart)`、`端口解析链`、`--force`。
References: [ADR-0007](0007-qemu-launch-profile-start-qemu-decision-seam.md)（QEMU launch profile——本 ADR 改的是 prepare 的端口解析，紧邻 profile/binary/firmware provisioning 之后，不改 launch profile 接口）、[ADR-0011](0011-ob-deploy-to-qemu-toplevel-ownership.md)（`cmd_deploy_to_qemu` 是本 ADR 端口复用机制的既有先例——直接赋 `QEMU_SSH_PORT` 等，本 ADR 在 start-qemu 照搬此机制 + 加 `-z` guard 修 CLI flag 覆盖漏洞）。

## Considered Options

1. **X-α：照搬 deploy 先例 + `-z` guard（接受）**——交互确认 kill 后，对每个 `QEMU_*_PORT` 做 `[[ -z "$QEMU_SSH_PORT" ]] && QEMU_SSH_PORT="$PIDFILE_SSH_PORT"`（Redfish/IPMI/HTTP 同理，HTTP 额外判 `!= "none"`），再调 `qemu_prepare_launch`。优先级链实际落地为 `CLI flag > 旧实例 > env > 默认`。优点：零新增变量族（复用 `QEMU_*_PORT` 既有 CLI 全局 + 既有 `PIDFILE_*`），机制贴合 deploy（同族命令一致）；`-z` guard 堵住"restart 时同时传 CLI flag 被旧端口覆盖"的静默 hazard。代价：path X 物理上无法实现"env > 旧实例"排序——注入到 CLI 层必然压过 env（deploy 亦如此）。注入路径的端口检查走既有 `check_ports_available`（无软特权，D5 翻转后 qemu.sh 不改）。deletion test：删掉这几行注入，痛点（2624 实例 restart 漂回 2623 被占）重现。
2. **候选 1：新增 `QEMU_RESTART_*` 全局族（拒绝）**——在 prepare 的端口解析式加第三格 fallback `${CLI:-${ENV:-${RESTART:-default}}}`，"-z guard + 注入 CLI 层"换成"`QEMU_RESTART_*` 独立命名空间 + 链上排序"。优点：能精确表达"env > 旧实例"`env` 优先排序。拒绝理由：(a) `cmd_deploy_to_qemu`（qemu_commands.sh:367-370）**已实现完全相同的端口复用语义**且用的是直接赋 `QEMU_SSH_PORT`（不引入新族）——新增 `QEMU_RESTART_*` 会让同族两个命令（start-qemu restart / deploy-to-qemu）对同一领域概念（"旧实例端口复用"）用**两套不同机制**，制造命名空间分裂与维护认知负担；(b) "env > 旧实例" 是 grill 第一轮选 β（显式信号压隐式）的结论，但 path X 下物理不可达——选 path X 即等于接受放弃此排序（见 D2 Q-D2-2）；(c) 零新增变量的 X-α 更贴合 deep module 抽取的"复用既有 seam 而非造新 seam"原则（OBSERVATIONS L58/70 方法论）。
3. **候选 1 变体：prepare 直读 `PIDFILE_*`（拒绝）**——不新增变量，prepare 的 ports 解析直接读 `PIDFILE_*`。问题：`qemu_prepare_launch` 当前是纯 prepare module（不感知"是否有 running 旧实例"这个 cmd 层概念），让它读实例快照变量（`PIDFILE_*`）是**泄露领域知识**——把"restart 上下文"语义渗进 prepare。且 `PIDFILE_*` 作用域是 `qemu_instance_load` 设的 global，prepare 在 non-restart 路径（首启、stale 清理后）被调时 `PIDFILE_*` 为空或残留旧值，prepare 须自行判"是否在 restart 上下文"——隐式耦合更脆。
4. **β 排序失败时的 α 候选：对称注入（拒绝，对应原 D6 α）**——`--force` 也注入旧端口（不区分交互确认与 `--force`）。问题：`--force` 的 canonical 定义是 "Kill existing instance without confirmation"——它是 **confirmation-gate modifier**，不是 **lifecycle declaration**。restart 是 lifecycle 概念（"把这个东西重新拉起来"），`--force` 修饰的是 confirmation（"别问我"），两者正交。让 `--force` 继承 restart 语义会混维、让端口行为依赖"上一实例用了啥"这种隐藏状态（更难预测）；且用户 `--force` 本意常常是"给我标准行为、别继承历史"。`--force`-restart 重新撞端口残留是其代价（已接受，用 `export OB_QEMU_IPMI_PORT=` 规避）。
5. **无软特权 / 硬特权（无特权最终采纳，对应 D5 翻转后 A；硬特权仍拒绝）**——无特权：旧端口注入了仍照走 `check_ports_available` + prompt，内核残留 socket 命中就弹 prompt，止痛点解一半；硬特权：无条件信任旧端口、完全跳过 check，第三方抢占时 deferred 到 `qemu_execute_launch` 的 setsid 失败（generic "QEMU failed to start"、根因藏 qemu_stderr）信息差大。本轮原拟"软特权"（occupant==`PIDFILE_PID` 豁免）作中间方案，二轮评审推翻（见 Consequences D5 翻转）：`ss -l` LISTEN-only 使触发条件（pid 活）与端口释放充要条件（pid 死）正好相反——进程已死时 socket 关、check 自然通过、软特权不需要触发；进程未死透时触发反而误豁免活进程、新 QEMU setsid bind 失败。叠加 owner=`?` 残留匹配不上 + 非 root `ss -p` 无 pid（F7），软特权期望效用为零或负。**最终采纳无特权（A）**：注入旧端口主治痛点（QEMU 优雅退出释放 socket），边缘残留场景弹 prompt 是正确引导而非 bug。

## Consequences

- **重启 (restart) 术语钉死**：restart = 同 machine 存在 running 旧实例 + 本次会 kill 它。stale 清理（`is_alive` 返 1=exited / 2=recycled）**不**注入（决策 1 "旧实例在跑=端口可用"前提崩了——PID 被回收时端口可能正跑别的程序）；无 `.pid` 文件的首次启动不注入（无源可沿）；`--force` 不注入（非 restart 语义）。注入**仅**服务 `cmd_start_qemu` 交互确认分支（`is_alive` 为 running + 用户敲 y）。
- **端口解析链（实际落地）**：`QEMU_LAUNCH_SSH_PORT="${QEMU_SSH_PORT:-${OB_QEMU_SSH_PORT:-2222}}"`（Redfish/IPMI 同构）。restart 时 `cmd_start_qemu` 在 `qemu_instance_stop` 后、`qemu_prepare_launch` 前注入：
  [[ -z "$QEMU_SSH_PORT" ]]    && QEMU_SSH_PORT="$PIDFILE_SSH_PORT"
  [[ -z "$QEMU_REDFISH_PORT" ]] && QEMU_REDFISH_PORT="$PIDFILE_REDFISH_PORT"
  [[ -z "$QEMU_IPMI_PORT" ]]   && QEMU_IPMI_PORT="$PIDFILE_IPMI_PORT"
  [[ -n "$PIDFILE_HTTP_PORT" && "$PIDFILE_HTTP_PORT" != "none" && -z "$QEMU_HTTP_PORT" ]] \
      && QEMU_HTTP_PORT="$PIDFILE_HTTP_PORT"

- **D5 翻转：放弃软特权（无特权，候选 5 选项 A）**。一轮 D5 曾选"软特权"（占用者 PID == `PIDFILE_PID` 豁免），二轮评审用证据推翻：(1) **语义反转**——`get_port_occupants` 用 `ss -tlnpH`/`ss -ulnpH`，`-l` 为 LISTEN-only。进程死→socket 关闭→`ss -l` 不报该端口→`check_ports_available` 自然通过，**软特权不需要触发**；进程未死透（D/zombie，stop 的 10s+SIGKILL 没杀掉）→ socket 仍 LISTEN、`ss -p` 仍关联 pid→软特权触发豁免→但端口真被活进程占→新 QEMU `setsid` bind 失败→exit 1 + 通用 "QEMU failed to start"（信息差，正是候选 5 拒绝硬特权时的同款缺点）。**触发条件（pid 活着）与"端口将释放"的充要条件（pid 已死）正好相反**——软特权在不需要时不触发、在最不该豁免时触发。(2) **痛点主治不靠它**——restart 注入旧端口（2624）后，QEMU 优雅退出立即释放 socket，痛点（撞默认 2623 历史残留）被"换用刚释放的旧端口"主治，软特权对此主治链无贡献。(3) **owner=`?` 场景匹配不上**（一轮已认）+ 非 root 下 `ss -p` 不输出 pid（F7）→ 实际运行环境大面积静默失效。结论：软特权期望效用为零或负，删比留好。**放弃后 `lib/qemu.sh` 的 `check_ports_available` / `prompt_for_available_port` 不改**，注入路径照走既有 conflict 报告 + exit 3 / prompt——注入旧端口主治主要痛点，边缘残留场景弹 prompt 是正确引导而非 bug。
- **软特权（已弃，留此作决策日志）的有效前提与限制**：(1) **有效前提**——仅当占用 socket 仍关联 pid 且该 pid == `PIDFILE_PID` 时豁免。痛点描述的 **owner=`?` 纯内核残留**（`ss -p` 关联不到 pid）恰匹配不上软特权（`grep -oP 'pid=\K[0-9]+'` 提取为空 → 比对永不成立）。**restart 痛点真正被治**靠的是「注入旧端口（2624）后 QEMU 优雅退出立即释放 socket、无 owner=`?` 残留」——软特权是 PIDFILE_PID 仍可解析时的**窄兜底**，非 ADR 字面曾暗示的「GC 滞后窗口主治」手段。(2) **root/NET_ADMIN 依赖**——`get_port_occupants` 的 `ss -tlnpH`/`ss -ulnpH` 的 `-p` 在非 root、无 NET_ADMIN 时不输出 `pid=`（与既有 `pid_info` 报告同病），软特权 pid 提取同步失效；非 root 环境下软特权退化为不触发（不误豁免、也不豁免），照走既有 conflict 路径。(3) **pid 复用残余风险**——`qemu_instance_stop` 删 `.pid` 文件但不清 `PIDFILE_PID` 变量（本设计依赖此前提）；若 stop 返回后该 pid 被内核复用给新进程且新进程恰好占同端口，软特权会误豁免第三方。窗口极小（stop 等到 `/proc/$pid` 消失或 SIGKILL），判为可接受残余风险。
- **与 `cmd_deploy_to_qemu` 的关系（不对称登记，不修 deploy）**：deploy（qemu_commands.sh:367-370）用的是"无条件赋值 `QEMU_SSH_PORT="$old_ssh_port"`"（X-β 排序：旧实例 > CLI），start-qemu restart 用"X-α（带 `-z` guard：CLI > 旧实例）"——两个命令对同一领域概念用**略不同的注入规则**。差异源于场景：deploy 极少"restart + CLI flag override 同时传"（它是 build+restart 编排），start-qemu 有此 hazard 故加 guard。**本 ADR 不改 deploy**（无 protocol 测试锁它、无 CLI 冲突 hazard 场景、path X 范围内不动）；差异记此登记为可接受的局部不对称。若未来 deploy 也要支持 CLI override 与 restart 并存，再回头对齐 guard。
- **两个不对称（需 ADR + protocol 测试锁防回潮，D5 翻转后从三个收敛为二）**：(a) 交互确认分支注入 vs stale 清理/`--force`/首启不注入（D4/D6）；(b) start-qemu 带 `-z` guard vs deploy 无 guard。两者都是刻意 trade-off、非对称缺陷——protocol 测试须各锁一条断言防未来 maintainer "修成对称"。
- **exit_contract**：本 ADR 不改 `lib/qemu.sh` / `lib/qemu_commands.sh` 的 exit 契约（仍为 exit seam / direct-exit module；`lib/qemu.sh` 在 D5 翻转后完全不动）。
- **可逆性**：决策逆转 = restart 分支删掉 `-z` guard 注入几行 → 回到现状（痛点复现）。本 ADR 是行为改进非结构性重构，低逆转成本；但两个不对称需同步有 protocol 测试网兜底，否则逆转的"修成对称"会悄回潮。
- **future-candidate（不违本 ADR）**：(1) deploy-to-qemu 若引入 CLI override + restart 并存场景，对齐本 ADR 的 `-z` guard；(2) restart 注入扩展到 stale 路径（现判 stale 不注入，若未来证明"stale 后端口大概率没被抢"、可放宽注入前提，但当前回收 PID（return 2）的危险让维持不注入更安全）；(3) `--force-restart` 显式 flag（若用户反馈"`--force` 时也想沿用端口"——区分 `--force`（kill 不问）与 `--force-restart`（kill 不问 + 沿用端口），但 YAGNI，等用户反馈触发）。
